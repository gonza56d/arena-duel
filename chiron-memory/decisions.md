# decision

A technical decision that was made and WHY (which alternatives were discarded).

## Every feel-affecting number lives in `src/config.ts` (`CONFIG: GameConfig`); simulation functions take a `GameConfig` parameter defaulting to `CONFIG`

What: Every feel-affecting number (arena size, spawn points, obstacle generation, player radius/speed/HP/heal, sim tick, per-skill stat tables, best-of options) lives in `src/config.ts` as one typed `CONFIG` object, and every simulation function takes a `GameConfig` parameter defaulting to `CONFIG` · Why: v1 is a tuning instrument — one edit must change behaviour everywhere; the injected parameter lets tests (and a future tuning UI) override values without touching the module · Where: src/config.ts, src/sim/*.ts (`cfg: GameConfig = CONFIG` on each function), src/arena.ts re-exports `ARENA_SIZE = CONFIG.arena.size` · Learned: `validateConfig()` runs at startup and in `createWorld`; it throws on fractional HP/heal/damage or impassable obstacle gaps so a mistyped value fails loudly instead of leaking a fractional HP mid-fight.

## Simulation runs on a fixed 10 ms tick with an accumulator and capped catch-up

What: The simulation advances in fixed `sim.tickMs = 10` steps fed by a real-time accumulator, with catch-up capped at `sim.maxTicksPerFrame` (drop time rather than replay seconds) · Why: every timing in the design doc is a multiple of 10 ms (bash wind-up 10 ms, dash 100 ms, speed per 100 ms), so 10 ms keeps them exact; a fixed step makes runs deterministic per (seed, config, inputs), which the future backend validation depends on · Where: src/config.ts (`sim`), src/game.ts (`advance`) · Learned: speed is stored as the doc's "units per 100 ms" and converted via `moveSpeedUnitsPerMs()`, so tuning reads exactly like the spec.

## Obstacles are axis-aligned rectangles placed by seeded rejection sampling with a guaranteed passable gap

What: Obstacles are axis-aligned rectangles generated by rejection sampling from a seeded mulberry32 RNG; each keeps ≥ `minGap` (≥ player diameter) from every other obstacle and the arena edge, and stays out of each spawn point's clearance circle · Why: circle-vs-AABB resolution is trivial and robust; the gap rule guarantees passability by construction without a path search; a seed fully determines the layout so tests are deterministic and two clients / the backend can share a layout by exchanging one number · Where: src/sim/obstacles.ts, src/sim/rng.ts, `CONFIG.arena.obstacles` · Learned: the count is "up to" — an obstacle that fails `maxPlacementAttempts` is skipped, so tests assert `≤ countMax`, not equality.

## HP model: integer-only, not clamped below 0, heal timer idle at full HP, damage does not reset the heal countdown by default

What: HP starts at `maxHp` and only ever changes by integers; `applyDamage` throws on non-integer or negative amounts; HP is not clamped at 0 (overkill stays visible, death is `hp <= 0`) but is clamped at `maxHp`; the heal timer is held at 0 while at full HP or dead, and taking damage does not restart it unless `player.healTimerResetsOnDamage` is true · Why: the doc requires integer HP and death at "0 or less"; whether damage interrupts healing is a feel choice, so it is a config flag rather than a hard-coded rule · Where: src/sim/player.ts, `CONFIG.player`.

## Unit tests use Vitest, colocated as `src/**/*.test.ts`, run with `npm test`

What: Vitest is the test runner (devDependency); tests sit next to the code as `src/**/*.test.ts` and run with `npm test` (`vitest run`) · Why: the simulation is pure TypeScript with no DOM, so fast node tests cover the acceptance criteria directly (speed, edges, obstacles, HP) including config-override tests that prove one constant changes behaviour · Where: package.json scripts, src/config.test.ts, src/sim/*.test.ts · Learned: `tsconfig` includes `src`, so test files are type-checked by `npm run typecheck` too; Vite ignores them in builds because nothing imports them.

## The record counters (`victories`, `games_played`) change only via `UserStore.IncrementRec…
